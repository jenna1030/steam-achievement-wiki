# 발표 가이드

## 한 문장 소개

Steam 공식 데이터만으로 부족한 도전과제 달성 조건을 사용자 공략과 결합하고,
검색부터 체크리스트까지 이어 주는 도전과제 전용 위키입니다.

## 문제와 해결

Steam은 도전과제 이름·설명·아이콘·전체 달성률은 제공하지만 DLC 필요 여부,
실제 공략, 놓치기 쉬움, 체감 난이도는 충분히 제공하지 않는다.

이 프로젝트는 데이터를 두 층으로 나눴다.

```text
Steam 공식 데이터
  게임 / 도전과제 / 아이콘 / 전체 달성률
              +
사용자 보완 데이터
  공략 / 태그 / 필요 조건 / 체감 난이도 / 체크리스트
              =
도전과제 탐색과 실행을 연결하는 위키
```

## 기술 선택과 이유

### Steam API 프록시

API Key 노출과 브라우저 CORS 문제를 피하기 위해 Steam 요청은 서버를 거친다.
동일한 요청 처리기를 로컬 Node 서버와 Vercel Functions가 함께 사용해 개발과
배포 환경의 로직 차이를 줄였다.

### TanStack Query와 Zustand 분리

Steam에서 받아오는 원격 데이터는 TanStack Query가 로딩·에러·캐시·중복 요청을
관리한다. 사용자가 즉시 수정하는 관심 게임·공략·투표·체크리스트는 Zustand가
관리하고 localStorage에 보존한다. 서버 상태와 클라이언트 상태의 생명주기가
다르기 때문에 한 저장소에 섞지 않았다.

### 공략 작성 검색의 Steam Store 어댑터 재사용

게임 검색과 공략 작성 검색이 서로 다른 Steam 앱 목록을 사용하면 결과와 이름이
달라질 수 있다. 두 화면이 같은 Steam Store 검색 어댑터를 사용하도록 통합하고,
공략 작성 화면은 두 글자 이상 입력했을 때 최대 30개만 받는다. Steam 전체 앱
목록 약 5만 개를 메모리에 올리던 방식보다 결과가 일관되고 서버 메모리 사용도
작다. 30개는 한 번에 렌더링해도 부담이 작은 상한이며, 더 큰 탐색은 게임 검색
페이지의 20개 단위 페이지네이션이 담당한다.

### 안정적인 도전과제 식별자

초기 구현은 `appid × 100000 + 배열 순번`을 ID로 사용했다. Steam 응답 순서가
바뀌면 같은 URL이 다른 도전과제를 가리킬 수 있어, `appid + Steam 내부
도전과제 이름` 기반 문자열 ID로 변경했다. 기존 숫자 URL과 localStorage
데이터는 상세 페이지에서 새 ID로 마이그레이션한다.

### 알 수 없음이 있는 요구 조건 모델

Steam API가 DLC·멀티플레이 조건을 주지 않는데 `false`로 저장하면
“본편만으로 가능”이라는 잘못된 정보를 표시하게 된다. 이를 `unknown`,
`required`, `not-required` 세 상태로 모델링했다. 공략 작성자가 확인한 경우에만
붉은 조건 배지를 노출한다.

### Steam 로그인 세션

OpenID callback에서 받은 SteamID를 URL/localStorage 로그인 값으로 사용하지
않는다. 서버가 OpenID 응답을 검증한 후 HMAC 서명된 HttpOnly 쿠키를 발급하고,
라이브러리 API는 해당 세션을 다시 확인한다. 비밀번호는 앱이 직접 받지 않는다.

### SteamID별 로컬 공략 분리

공략에 `ownerSteamId`를 저장하고 읽기·수정·삭제·개수 계산에서 현재 로그인
SteamID를 함께 비교한다. 같은 브라우저를 여러 Steam 계정이 사용해도 공략이
섞이지 않는다. 기존 `ownerSteamId` 없는 공략은 첫 로그인 계정에 한 번 귀속해
사용자가 작성한 데이터를 잃지 않게 했다. 다만 이는 클라이언트 분리이므로
권한 보안이나 기기 간 동기화를 제공하는 데이터베이스 대체재는 아니다.

### 요청 비용 제어와 지연 로딩

페이지를 `React.lazy`로 나누고, 홈의 Recharts 차트는 화면에서 320px 안쪽에
접근할 때만 추가로 import한다. 이 결과 홈 페이지 자체 청크는 약 63KB에서
6.9KB로 줄었다. 마이페이지는 라이브러리 카드마다 상점 상세 API를 다시
호출하던 N+1 요청을 제거하고 Steam CDN 이미지를 사용한다. 전체 라이브러리의
도전과제 집계도 첫 20개만 자동 조회하고, 사용자가 “전체 기록 집계”를 눌렀을
때만 나머지를 순차 조회한다.

### strict와 자동 테스트

TypeScript `strict`는 nullable 값, 함수 인자, 타입 추론의 빈틈을 빌드 전에
오류로 바꾼다. 자동 테스트는 Vitest로 안정 ID, SteamID별 공략 필터링, 홈 추천
규칙처럼 사람이 매번 눌러 보기 어려운 순수 로직을 반복 검증한다.
`npm run check` 하나로 lint, 8개 테스트, strict 빌드가 실행되며 CI도 같은
명령을 사용한다. 테스트가 브라우저 시연을 완전히 대신하는 것은 아니므로
로그인과 무한 스크롤은 별도 수동 점검 대상으로 남긴다.

### Steam API 레이트 리밋

학생 프로젝트의 1인 시연과 소규모 접근을 기준으로, IP·라우트별 1분 창을
사용한다. 검색은 비용이 커서 Store 검색 20회, 공략 앱 검색 30회로 제한하고
게임·도전과제·프로필 조회는 60회로 둔다. 모든 Steam fetch에는 12초 타임아웃을
적용한다. 제한을 넘으면 `429`와 `Retry-After`를 반환한다. 현재 구현은
인스턴스 메모리 기반이라 Vercel 인스턴스 간 전역 제한은 아니며, 실제 서비스
규모에서는 Upstash Redis나 Vercel WAF 같은 공유 저장소 기반 제한으로 바꾼다.

### 홈 추천의 범위

홈에는 정보 밀도를 위해 게임을 최대 3개만 노출하지만 더 이상 특정 3개만
고정하지 않는다. 사용자의 관심 게임을 우선하고 부족한 자리만 기본 게임으로
채운다. 추천 점수는 전체 달성률, 예상 시간, 관심 게임 여부, 놓치기 쉬움
패널티를 사용하며 DLC·멀티플레이 필수 항목은 제외한다. 체감 난이도는 현재
전체 달성률에서 파생되므로 같은 신호를 두 번 가산하지 않는다.

## 시연 순서

1. 홈에서 게임 검색
2. 실제 Steam Store 장르와 도전과제 유무 필터
3. 게임 상세에서 아이콘·달성률 정렬·숨김 표시
4. 도전과제 상세에서 체크리스트 추가
5. 난이도 투표 후 다른 항목으로 재투표, 투표 취소
6. 공략 작성에서 태그와 “본편만으로 가능” 조건 선택
7. 게임 상세 모아보기 카드에 태그와 붉은 조건 배지가 반영되는지 확인
8. Steam 로그인 후 SteamID별 공략 수와 공개 라이브러리 확인
9. 마이페이지에서 일부 집계와 “전체 기록 집계”의 차이 확인

## 질문 대응

### 왜 데이터베이스를 쓰지 않았나요?

이번 평가의 핵심인 React 상태 관리와 API 연동 흐름을 우선 검증하기 위해 개인
데이터는 localStorage로 범위를 제한했다. 대신 계정 간 커뮤니티 기능은 현재
한계로 명시했고, 다음 단계에서는 사용자·공략·투표 테이블과 권한 검증을
백엔드로 이동할 계획이다.

### localStorage인데 계정 기능이라고 할 수 있나요?

현재 단계는 로그인한 SteamID를 공략의 소유자 키로 사용해 같은 브라우저 안에서
계정을 분리한다. 서버가 쓰기 권한을 검증하는 구조는 아니므로 “계정별 로컬
분리”라고 표현하는 것이 정확하다. 실제 다중 사용자 위키로 확장할 때는
`users`, `guides`, `votes` 테이블과 서버 권한 검증이 필요하다.

### 달성률이 낮으면 무조건 어려운가요?

그렇지 않다. 달성률은 공식 데이터이고 체감 난이도는 사용자 투표로 분리했다.
현재 추천은 전체 달성률, 예상 시간, 관심 게임 여부와 공략 조건을 사용한다.
투표 데이터가 충분히 쌓이면 체감 난이도를 별도 신호로 추가할 수 있다.

### Steam API 실패 시에는 어떻게 되나요?

TanStack Query의 로딩/에러 상태를 화면에 표시하며 API Key는 서버에만 둔다.
공략과 체크리스트는 로컬 데이터이므로 Steam 요청과 별도의 수명주기를 가진다.

### 공략 검색 결과를 30개로 자른 이유는 무엇인가요?

드롭다운은 선택 보조 UI라서 검색 전체 결과를 담지 않는다. 두 글자 이상 입력한
검색어에 대해 최대 30개만 렌더링해 브라우저와 서버 비용을 제한했다. 더 많은
결과를 탐색하는 흐름은 게임 검색 페이지의 20개 단위 페이지네이션으로 분리했다.

### 왜 레이트 리밋이 라우트마다 다른가요?

Steam Store 검색은 HTML 파싱과 상세 정보 보강이 포함돼 상대적으로 비싸고,
단일 게임·프로필 조회는 캐시 적중 가능성이 높다. 그래서 검색은 분당 20~30회,
일반 조회는 분당 60회로 차등 적용했다. `429`를 실제 확인했으며, 운영 트래픽이
생기면 로그를 보고 상한과 창 크기를 다시 조정한다.

### 자동 테스트와 strict는 각각 무엇을 막나요?

strict는 “값이 없을 수 있는데 있다고 가정하는 코드” 같은 타입 결함을 컴파일
단계에서 막는다. 자동 테스트는 타입으로 표현할 수 없는 업무 규칙, 예를 들어
“A 계정은 B 계정 공략을 볼 수 없다”와 “추천은 3개를 넘지 않는다”를 검증한다.
둘은 역할이 달라 함께 사용한다.

- 변경: Store 검색 어댑터 재사용, `ownerSteamId`, 선택 집계와 차트 지연 로딩

- 품질: strict, Vitest 8개, lint/build CI, 브라우저 주요 흐름 검증
- API 안전: 12초 타임아웃, 라우트별 레이트 리밋, 입력 범위 제한
- 배포: 로컬/Vercel 공용 API 처리기와 환경변수 분리
- 한계: 공략 소유권은 현재 브라우저 범위이고 전역 레이트 리밋은 후속 범위

## 확인된 의존성 보안 예외

2026-07-30 기준 `npm audit`에는 `react-router`의 실험적 RSC Action 경로에
대한 CSRF 권고 `GHSA-qwww-vcr4-c8h2` 2건이 남는다. 이 프로젝트는 Vite SPA의
`BrowserRouter`만 사용하고 RSC API나 서버 Action을 사용하지 않아 해당 실행
경로를 사용하지 않는다. `npm audit fix --force`가 제안하는 7.11.0 다운그레이드는
권고 범위와도 모순되므로 자동 적용하지 않고, 배포 전 수정 버전 게시 여부를
다시 확인한다.
