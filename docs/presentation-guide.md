# 발표 가이드

이 문서는 발표 순서와 질문 대응을 위한 메모입니다. 실행·배포 방법은
[프로젝트 README](../README.md), 상세 구현 근거는
[설계 문서](architecture.md)를 참고합니다.

## 1. 한 문장 소개

Steam의 게임·도전과제 데이터에 사용자 공략과 개인 체크리스트를 결합해,
도전과제를 찾는 단계부터 실제로 달성하는 과정까지 관리하는 웹
애플리케이션입니다.

## 2. 해결하려는 문제

Steam에서 확인할 수 있는 정보와 실제 달성에 필요한 정보 사이에는 차이가
있습니다.

| Steam에서 확인 가능 | 사용자가 추가로 필요한 정보 |
| --- | --- |
| 게임과 도전과제 이름 | 실제 달성 순서 |
| 도전과제 설명과 아이콘 | DLC·멀티플레이 필요 여부 |
| 전체 유저 달성률 | 놓치기 쉬운 조건과 버그 주의 |
| 개인 달성 여부 | 힌트와 스포일러 조절 |

이 프로젝트는 Steam 데이터를 임의로 바꾸지 않고 사용자 보완 데이터와
분리해서 보여 줍니다. 사용자는 게임을 검색하고, 도전과제를 확인한 뒤, 필요한
공략만 단계별로 열어 보고, 체크리스트에서 진행 상태를 관리할 수 있습니다.

## 3. 핵심 사용자 흐름

```text
게임 검색
  → 게임 상세와 도전과제 필터
  → 도전과제 상세
  → 공략 비교와 단계별 열람
  → 체크리스트 저장·메모
  → Steam 로그인 후 내 달성 기록 확인
```

각 화면을 별도 기능으로 나열하는 대신 탐색, 정보 보완, 실행, 회고가 하나의
흐름으로 이어지게 설계했습니다.

## 4. 발표에서 강조할 설계 선택

### 4.1 Steam 요청을 서버로 분리

Steam API Key를 React 번들에 넣으면 누구나 개발자 도구에서 확인할 수 있고
브라우저 CORS 문제도 발생합니다. 따라서 로컬에서는 Node 프록시, 배포에서는
Vercel Functions가 Steam 요청을 대신 수행합니다. 두 환경은 같은 요청
처리기를 사용해 동작 차이를 줄였습니다.

발표 표현:

> Steam API Key를 숨기기 위해 별도 요청 계층을 두었고, 로컬과 Vercel이 같은
> 로직을 사용하도록 구성했습니다.

### 4.2 서버 상태와 클라이언트 상태 분리

Steam 응답은 TanStack Query가 캐시, 로딩, 오류, 페이지네이션을 관리합니다.
공략, 투표, 체크리스트처럼 사용자가 즉시 바꾸는 값은 Zustand와 localStorage가
관리합니다.

두 종류의 데이터는 변경 주체와 수명이 다르기 때문에 하나의 store에 섞지
않았습니다.

### 4.3 SteamID별 공략 분리

공략에 `ownerSteamId`를 저장하고 현재 로그인한 SteamID와 비교해 조회·수정·삭제
범위를 나눕니다. 같은 브라우저에서 계정을 바꾸더라도 공략이 섞이지 않습니다.

다만 이는 로컬 데이터 구분이며 서버 권한 검증은 아닙니다. 발표에서는 “계정별
로컬 분리”라고 표현하는 것이 정확합니다.

### 4.4 알 수 없음을 보존하는 조건 모델

Steam API가 DLC 필요 여부를 주지 않는데 기본값을 `false`로 두면 확인하지 않은
정보를 “본편만으로 가능”이라고 잘못 표시하게 됩니다. 조건을 `알 수 없음`,
`필요`, `불필요`로 나누고 공략 작성자가 확인한 경우에만 붉은 조건 배지를
보여 줍니다.

### 4.5 안정적인 도전과제 ID

배열 순번으로 ID를 만들면 Steam 응답 순서가 바뀔 때 URL과 localStorage가
다른 도전과제를 가리킬 수 있습니다. 현재는 `appid + Steam 내부 도전과제
이름`을 조합해 같은 도전과제가 같은 ID를 유지하게 했습니다. 기존 숫자 ID는
새 형식으로 마이그레이션합니다.

### 4.6 검색 페이지네이션

Steam Store 검색은 25개 경계로 다음 결과를 반환합니다. 20개를 다음 시작점으로
사용했을 때 첫 페이지가 한 번 반복되는 문제를 실제 응답 비교로 확인했습니다.

- 요청 크기와 다음 시작점을 25 단위로 통일
- 서버가 명시적인 `nextStart` 반환
- 클라이언트가 `appid` 기준으로 중복 제거
- 로딩 중 기존 카드 그리드의 빈 칸부터 스켈레톤 표시

오류를 UI에서 가리는 데 그치지 않고 외부 데이터 소스의 페이지 규칙에 맞게
수정한 사례로 설명할 수 있습니다.

### 4.7 전체 달성 기록 성능

마이페이지는 공개 라이브러리의 모든 게임에 대해 개인 도전과제 기록을
확인합니다. 한 번에 전부 병렬 요청하면 Steam과 Vercel에 부담이 커지므로:

- 서버에서 30개 게임 단위로 페이지 처리
- 페이지 안에서는 최대 6개 Steam 요청만 병렬 실행
- 클라이언트는 250ms 간격으로 다음 페이지 자동 요청
- 집계 중에는 확인한 게임 수를 progressbar로 표시

사용자는 버튼을 반복해서 누르지 않아도 최종 전체 집계를 얻고, 요청량은
제어됩니다.

| 기획 기능 | 현재 상태 | 구현 방식 |

| 공략 CRUD | 완료 | SteamID별 localStorage |
| 스포일러 단계 | 완료 | 힌트와 자세한 공략 단계 |
| 공략 평가 | MVP 완료 | 좋아요·싫어요·신고의 브라우저 저장 |
| 공략 조건 | 완료 | DLC·멀티 3상태 모델과 2회차 태그 |

| 쉬운 도전과제 추천 | MVP 완료 | 관심 게임 우선, 최대 3개 |
| Steam 로그인·라이브러리 | 완료 | OpenID와 공개 프로필 |

공략 평가의 “MVP 완료”는 실제 여러 사용자가 공유하는 서버 기능이라는 뜻이
아닙니다. 반응과 신고가 현재 브라우저에 저장되고 예시 공략으로 다중 공략
화면을 시연할 수 있다는 범위입니다.

`npm run check` 하나로 다음 검사를 실행합니다.

테스트는 UI 모양보다 변경될 가능성이 높은 도메인 규칙을 우선합니다.

- 도전과제 안정 ID와 이전 데이터 변환
- 계정별 공략 소유권
- localStorage 스키마와 버전
- 공략 반응·신고·좋아요 순위
- 추천 최대 3개
- Store 페이지 중복 제거

GitHub Actions도 pull request와 `main` push에서 같은 검사를 수행합니다.

## 8. 시연 순서

### 1. 홈

- 서비스가 해결하려는 문제를 한 문장으로 소개
- 검색창이 넓은 화면과 분할 화면에서 어떻게 배치되는지 확인
- 관심 게임을 반영한 쉬운 도전과제 추천 3개 확인

### 2. 게임 검색

- 게임명 검색
- 장르·태그 검색 상자에서 `공포` 입력
- 도전과제 `1~10개`, `11~50개`, `51개 이상` 필터
- 더보기에서 기존 카드 다음에 스켈레톤이 이어지는지 확인

### 3. 게임 상세

- 이미지, 장르, 출시일, 상점 링크
- 도전과제 아이콘과 전체 달성률
- 달성률 정렬과 공략 태그 필터
- 개인 기록이 있으면 달성 여부와 100% 완료 표시

### 4. 도전과제 상세와 공략

- 예시 공략이 사용자 공략과 배지로 구분되는지 확인
- 좋아요·싫어요 수를 보고 공략 펼치기
- 힌트와 자세한 공략을 단계별로 확인
- 공략 작성에서 예상 시간 범위와 조건 태그 선택

### 5. 체크리스트

- 도전과제 저장
- 진행 상태와 메모 변경
- 좋아요가 가장 많은 공략의 힌트·자세한 공략 확인

### 6. 마이페이지

- Steam 프로필 이미지와 공개 라이브러리
- 전체 달성 기록 집계 progress
- 달성 도전과제 수와 100% 완료 게임
- 정렬과 라이브러리 무한 스크롤
- 내가 작성한 공략 모아보기

## 9. 예상 질문

### 왜 데이터베이스를 사용하지 않았나요?

이번 프로젝트는 BCSD 프론트엔드 트랙에서 React 상태 관리, API 연동, 비동기
UX를 검증하는 것이 우선이었습니다. 개인 데이터는 localStorage로 범위를
제한하고 버전·스키마 검증을 보강했습니다. 실제 커뮤니티로 운영한다면
`users`, `guides`, `reactions`, `reports`를 데이터베이스로 옮기고 서버에서
권한을 검증해야 합니다.

### localStorage인데 계정 기능이라고 할 수 있나요?

SteamID를 공략 소유자 키로 사용해 같은 브라우저 안에서 계정을 분리합니다.
서버가 쓰기 권한을 검증하는 구조는 아니므로 “SteamID별 로컬 분리”가 정확한
표현입니다.

### TanStack Query와 Zustand를 왜 같이 사용했나요?

TanStack Query는 서버에서 받아오는 데이터의 캐시와 요청 상태를 관리하고,
Zustand는 사용자가 즉시 바꾸는 로컬 상태를 관리합니다. 변경 주체와
생명주기가 달라 책임을 나눴습니다.

### 공략 작성 검색을 30개로 제한한 이유는 무엇인가요?

선택 상자는 검색 전체 결과를 탐색하는 화면이 아니라 목표 게임을 빠르게 고르는
보조 UI입니다. 두 글자 이상 입력, 300ms debounce, 최대 30개로 브라우저와
서버 비용을 제한하고 더 넓은 탐색은 게임 검색 페이지에서 담당합니다.

### 전체 달성 기록이 오래 걸리는 이유는 무엇인가요?

Steam은 전체 라이브러리의 도전과제를 한 번에 집계한 응답을 주지 않아
도전과제를 지원하는 게임별로 확인해야 합니다. 요청 폭주를 피하기 위해 30개
페이지와 동시성 6으로 제한하고, 진행률을 먼저 보여 준 뒤 자동 완성합니다.

### 달성률이 낮으면 무조건 어려운가요?

아닙니다. 전체 달성률은 Steam 사용자 전체의 통계이고 체감 난이도는 별도
투표입니다. 추천에서는 달성률, 예상 시간, 관심 게임, DLC·멀티플레이 조건을
함께 사용합니다.

### 예시 공략을 실제 데이터처럼 보이게 만든 것 아닌가요?

예시 공략은 `source: example`인 읽기 전용 데이터이며 화면에서 “예시 공략”
배지로 표시합니다. 다중 공략 정렬과 펼치기 UX를 시연하기 위한 데이터이지
Steam이나 실제 다른 사용자가 제공한 데이터라고 표현하지 않습니다.

### 왜 Tailwind나 Styled Components를 제거했나요?

프로젝트가 이미 디자인 토큰과 역할별 CSS를 사용하고 있어 스타일 방식을 하나로
통일하는 편이 유지보수에 유리했습니다. Tailwind는 로그인 기술이 아니라 CSS
유틸리티 도구이며 Steam OpenID와는 관계가 없습니다.

### Steam API 실패 시에는 어떻게 되나요?

TanStack Query가 로딩과 오류 상태를 관리하고, 화면은 다시 시도할 수 있는 오류
UI를 표시합니다. 공략과 체크리스트는 별도 localStorage 데이터라 Steam
요청 실패와 독립적으로 유지됩니다.

### 레이트 리밋이 운영 환경에도 충분한가요?

현재는 1인 시연과 소규모 접근을 위한 인스턴스 메모리 기반 제한입니다. 여러
Vercel 인스턴스 전체에 공통으로 적용되지 않습니다. 지속 운영한다면 Upstash
Redis나 Vercel WAF처럼 공유 상태를 사용하는 방식으로 바꿔야 합니다.

## 10. 표현할 때 주의할 점

- 게임 목록은 “Steam 공식 앱 목록”보다 “Steam Store 검색 결과”라고
  표현합니다.
- 도전과제 이름·아이콘·전체 달성률은 “Steam Web API에서 조회”라고
  표현합니다.
- 공략·투표·평가·신고는 “현재 브라우저에 저장”된다고 밝힙니다.
- `ownerSteamId`는 서버 권한이 아니라 “계정별 로컬 분리”입니다.
- 예시 공략은 실제 커뮤니티 데이터로 소개하지 않습니다.
- 레이트 리밋은 “운영급 전역 제한”이 아니라 “MVP 안전장치”입니다.

## 11. PR 설명에 사용할 요약

### 문제

- Steam 데이터만으로 실제 달성 조건을 알기 어려움
- 검색 화면별 게임 데이터가 달라질 가능성
- 응답 순서와 로컬 데이터 형식 변경에 취약
- 전체 라이브러리 집계의 많은 네트워크 요청

### 해결

- Steam 기본 데이터와 사용자 공략 데이터 분리
- 공통 Store 검색 어댑터와 25개 페이지 경계
- 안정 도전과제 ID와 localStorage 마이그레이션
- SteamID별 공략 분리
- 전체 기록 페이지 처리와 제한된 동시성
- 로딩 skeleton, 전역 오류 복구, 접근성 보강

### 사용자 가치

- 게임 검색부터 공략과 체크리스트까지 이어지는 흐름
- 원하는 수준의 스포일러만 확인
- 여러 공략을 반응 수로 비교
- 자신의 Steam 라이브러리와 달성 기록 확인

### 현재 한계

- 커뮤니티 데이터는 현재 브라우저 범위
- 비공개 Steam 프로필은 개인 기록 조회 불가
- 댓글과 계정 간 동기화는 미구현
- 레이트 리밋은 인스턴스 메모리 기반
